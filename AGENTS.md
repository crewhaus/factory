## The three architectural pillars

Every change in this repo must respect three invariants. They exist because in 2026-Q2 a critique surfaced that the implementation had drifted from the founding thesis on each axis; the remediation is documented in the corresponding sections of [build-roadmap.md](https://github.com/crewhaus/docs/blob/main/build-roadmap.md) and the invariants are codified here so future contributors stay anchored.

### Pillar 1 — The compiler is the protagonist

Crewhaus is a **meta-harness compiler**, not "yet another agent loop." Specs flow through `parseSpec → lower → applyPasses → emit` ([packages/compiler/src/index.ts](packages/compiler/src/index.ts)). The IR is a discriminated union — `IrNode = IrV0 | IrWorkflowV0 | IrChannelV0 | IrGraphV0 | IrManagedV0 | IrPipelineV0 | IrCrewV0 | IrResearchV0 | IrBatchV0 | IrVoiceV0 | IrBrowserV0 | IrEvalV0 | IrChainV0 | IrChainGameV0` ([packages/ir/src/index.ts:2807](packages/ir/src/index.ts:2807)) — and each target shape consumes its own IR variant.

**Contributor rules:**

1. **New target shapes start at the IR**, not at codegen. Add an `Ir<Target>V0` type to the discriminated union, add a `lower` case, add an `emit<Target>(ir: Ir<Target>V0)` function, register it in `emit()`. The `assertNever(ir)` exhaustive check at [packages/compiler/src/index.ts:6620](packages/compiler/src/index.ts:6620) keeps you honest.
2. **Targets receive their typed IR variant**, never the raw spec. If you reach into `spec.foo` from a target emitter, you've broken the polymorphism — push the field into the IR variant instead.
3. **IR-level optimizations live in `packages/ir-passes/`** as `(IrNode) → IrNode` functions with a type-guard for the variants they touch. See `redundantMcpServerCollapse` at [packages/ir-passes/src/index.ts:175](packages/ir-passes/src/index.ts:175) for the template.
4. **Eval-driven mutations do NOT go in `ir-passes`.** They patch the spec, not the IR — see Pillar 2.
5. **The roadmap, briefs, and recipes for a new feature must cite its IR variant.** If you find yourself documenting something without an IR variant, you're probably adding a runtime feature without first deciding where it lives in the compiler.

### Pillar 2 — Eval is active, not passive

The empirical signal that the harness layer can deliver measurable accuracy gains is DSPy's MIPRO result (+13% on five of seven multi-stage programs, cited in [AI-Harness-Systems.md](https://github.com/crewhaus/docs/blob/main/AI-Harness-Systems.md)). Crewhaus's eval stack must close the loop: eval failures must produce *spec patches*, not just HTML reports.

The active-optimization layer:

- **[packages/eval-runner](packages/eval-runner)** measures.
- **[packages/prompt-optimizer](packages/prompt-optimizer)** searches the mutation space via a `MutationProvider` interface. Two providers ship: `RuleBasedMutationProvider` (deterministic, default for tests) and `ClaudeMutationProvider` ([packages/prompt-optimizer-claude](packages/prompt-optimizer-claude), model-driven rewriting).
- **[packages/spec-patch](packages/spec-patch)** carries `SpecPatch` + `applySpecPatch(yaml, patch)`, which uses the YAML CST to preserve comments + key order on write-back.
- **[packages/eval-optimizer-orchestrator](packages/eval-optimizer-orchestrator)** wires them together.
- **`crewhaus optimize <spec>`** is the user-facing entry; default emits a patch JSON + HTML diff, `--write-back` rewrites the YAML in place.

**Contributor rules:**

1. **Spec parameters that should be optimizable** must be listed in `OPTIMIZABLE_PATHS` ([packages/spec-patch/src/index.ts](packages/spec-patch/src/index.ts)). If you add a new spec field that affects eval quality (chunkOverlap, defaultK, temperature, instructions), add the path or the optimizer can't reach it.
2. **Patches mutate the spec, never the IR.** The compiler's `lower()` does destructive normalization (sort, freeze, env-var rewriting); IR-level patches can't round-trip back to YAML.
3. **The rule-based provider stays the default in tests** so test fixtures are deterministic. The model-driven Claude provider is opt-in via `--mutator claude`. The `--budget-usd` cost-gate backed by `cost-tracker` now ships: the orchestrator threads a `cost-tracker`-priced running total through the search, estimates each call's worst-case cost before issuing it, and stops before a mutation call that would exceed the budget — composing with the `iterations` cap (whichever bound is hit first ends the run). Rule-based runs make no model calls and report `$0`.
4. **Eval reports without a patch are passive grading** — that's fine for canary gates and dashboards, but the system's promise is *active* optimization. Do not let the optimization loop fall out of date with the rest of the eval stack.
5. **A knob that sets the bar the optimizer is graded against is never optimizable.** A floor, an allowlist, or the rule for what counts as evidence stays out of `OPTIMIZABLE_PATHS` and gets a row with its reason in `HUMAN_OWNED_PATHS` beside it; an optimizer that can lower its own bar learns to blind its critic. `provability.level` and `provability.on_fail` are also `OPTIMIZER_REFUSED_LEAVES` rows, so no wider entry and no block patch can move them, and `crewhaus doctor --philosophy-alignment` fails if `provability.level` becomes optimizable. The `provability:` block's four dials (`threshold`, `max_retries`, `grounded.coverage`, `grounded.window_tokens`) are the template for a quality knob that may be tuned.

### Pillar 3 — Security is a fabric, not a perimeter

Section 18's "safety floor" is necessary but not sufficient. Untrusted content can enter the system at any boundary — MCP responses, sub-agent returns, channel inbound messages, federation peer payloads, skill bodies loaded from disk, compaction summaries that absorbed earlier attacker text — and an attacker who controls one of those boundaries can lateral-move across the system if the boundary doesn't re-verify.

The fabric has **two symmetric halves**: a source side (classify content coming in) and a sink side (classify content going out). The OpenAI 2026-05 prompt-injection paper and SACR's 2026 runtime-security report converge on the same insight: source classification is necessary but not sufficient; an attacker who controls a source AND an accessible sink can lateral-move across the agent's permissions even when every individual permission check passes. The egress fabric (recommendation A, v0.2.x) is the symmetric companion that closes that loop.

**Source-side chokepoint** — [packages/boundary-classifier](packages/boundary-classifier). It wraps `prompt-injection-detector` with `TrustOrigin` metadata (`"user" | "mcp" | "subagent" | "channel" | "federation" | "skill" | "compaction" | "tool" | "chain" | "memory" | "consult"`), a content-hash LRU cache, and a configurable severity policy (default: block on malicious, warn on suspicious). `RunContext.originStack` carries the origin chain so trace events record it. After a non-blocked verdict, the boundary site also calls `tagContent(ctx, content, origin)` which populates `RunContext.dataLineage` for the sink-side check.

| Source site | Origin | Where |
|---|---|---|
| MCP tool responses, and tool definitions (name, description, every schema key and string) at registration | `"mcp"` | [packages/tool-mcp](packages/tool-mcp) |
| Sub-agent `finalMessage` | `"subagent"` | [packages/sub-agent-spawner](packages/sub-agent-spawner) |
| Inbound channel text | `"channel"` | [packages/channel-adapter-base](packages/channel-adapter-base) (via the generated channel-bot `runTurn`) |
| Federation peer payloads | `"federation"` | [packages/federation-router](packages/federation-router) |
| Skill bodies | `"skill"` | [packages/skills-registry](packages/skills-registry) |
| Compaction summaries | `"compaction"` | `packages/compaction-*` |
| Tool results | `"tool"` | [packages/runtime-core](packages/runtime-core) |
| On-chain payloads / receipts | `"chain"` | [packages/target-onchain](packages/target-onchain), [packages/target-onchain-game](packages/target-onchain-game), [packages/wallet-engine](packages/wallet-engine) |
| Recalled wiki/fact bodies | `"memory"` | [packages/tool-wiki](packages/tool-wiki) (wiki reads, inside the tool; list rows one by one and side by side, so an injection split across two rows is caught); [packages/runtime-core](packages/runtime-core) (auto-recalled fact, wiki and session-summary lines, per line and then joined, before they enter the system region — `renderRecalledMemory`) |

**Sink-side chokepoint** — [packages/egress-classifier](packages/egress-classifier). On every external-scope tool call (`tool.scope === "external"`), `runtime-core` calls `classifyEgress(payload, ctx, { sinkId, sinkScope })`. The classifier scans `RunContext.dataLineage` for substring matches and folds the per-origin policy across all hits. The default policy is *permissive on `"user"` content, warn on configured sinks, block on dynamic sinks*. Three audit outcomes land in the trace bus and audit-log: `"egress-passed" | "egress-warned" | "egress-blocked"`.

|---|---|---|
| HTTP fetch | [packages/tool-fetch](packages/tool-fetch) | `"external"` |
| Web search / fetch | [packages/tool-web](packages/tool-web) | `"external"` |
| MCP tool call | [packages/tool-mcp](packages/tool-mcp) | `"external"` |
| Channel send | [packages/tool-message-channel](packages/tool-message-channel) | `"external"` |
| EVM tx broadcast | [packages/tool-evm-tx](packages/tool-evm-tx) | `"external"` |
| Image generation upload | [packages/tool-image-generation](packages/tool-image-generation) | `"external"` |

**Intent gate** — orthogonal third layer. Tools that set `requireJustification: true` (for example `SendMessage`, `EvmSendTransaction`, `HttpRequest`, `EmailSend`) demand the model supply a `justification` string with each call. The contract is advertised, not just enforced (#386): at request-build time `runChatLoop` augments the gated tool's model-facing input schema with a required `justification` string property (unless the tool's own schema already declares one) and strips a runtime-injected field from the input again before it reaches the tool's validator or a remote MCP server — see `withJustificationField`/`stripJustificationField` in [packages/tool-catalog](packages/tool-catalog). `permission-engine`'s `evaluateJustification` checks it against the spec's `instructions` (the goal an attacker cannot influence) via a configurable judge — rule-based by default (`ruleBasedJustificationJudge`), model-backed in production (`@crewhaus/justification-judge-claude`, selected via `runChatLoop({ justificationJudge })`, the spec's `security.justification.judge`, or `--justification-judge`). The gate publishes a `permission_decision` trace event (carrying first-class `judgeModel` + `justificationConfidence`) for live observability AND — when a durable sink is wired via `runChatLoop({ justificationAuditSink })` — appends a hash-chained `permission_justification_evaluated` record (verbatim `{ toolName, justification, verdict, reason, judgeModel, confidence? }`) to `@crewhaus/audit-log`. The CLI `run` path opens that sink at `.crewhaus/audit` by default (opt out with `--no-justification-audit`); a compiled cli bundle whose spec declares `security.justification` builds the same judge through the same `createJustificationJudgeFromSlot` and opens the same log (opt out with `CREWHAUS_SECURITY_AUDIT=0`). SACR's three-layer model (deterministic governance → behavioral analysis → non-deterministic governance) lands its third layer here; recipe [demos/walkthroughs/53-justification-gates.md](https://github.com/crewhaus/demos/blob/main/walkthroughs/53-justification-gates.md) walks through it.

**Runtime-state floor** (0.8.0) — the provability gate and `continuity.proof` take the runtime's own record as evidence, which proves nothing if the agent can rewrite it. Every run computes its state roots (`runtimeStateRoots` in runtime-core: the session logs, the spilled tool results, the proof bundles), and permission-engine denies, before any rule is read, a call that is not read-only and writes inside one, or acts on everything beneath a workspace directory that holds one (`EvaluateOptions.protectedRoots`); only `bypass`, which consults nothing, skips it. The floor reads the operative fields a call writes. A tool that writes beneath a directory it names — `CopyPath`, `MovePath`, `RemovePath`, `ArchiveExtract`, `GitApplyPatch`, `StateImport`, `StoreMigrate` — lands where the floor cannot see, so it checks its own targets against the roots on its bridge (`RuntimeBridge.protectedRoots`) and refuses in every mode, `bypass` included. `Bash` and `RunCommand`, whose writes no layer can see, are the documented residual. The gate itself ingests nothing new: it reads bodies that were classified at their own origin when they arrived, and its retry nudge carries the model's own sentences and evidence ids, never fetched text, so it adds no `TrustOrigin`.

**Contributor rules:**

1. **Any new module that ingests external content registers a `TrustOrigin`** in [packages/boundary-classifier/src/index.ts](packages/boundary-classifier/src/index.ts) (the union AND its `ORIGIN_DEFAULT_POLICY` row; the mirrored union in `packages/run-context` and the egress severity matrix are compile-checked against it, and the test arrays derive from `TRUST_ORIGINS` — the six-site checklist is in the union's docblock), calls `classifyBoundary` before the content reaches a model call or a tool result, AND calls `tagContent(ctx, content, origin)` after a non-blocked verdict so the sink-side classifier sees it.
2. **Any new tool that crosses a process or network boundary sets `scope: "external"`** in its `ToolDefinition`, and **declares `ioCapability: "network" | "process"`** (the *fact* of crossing a boundary, distinct from `scope`, the *policy*). Tools default to `"internal"` at normalization, so forgetting `scope` is silently insecure — the §41 `crewhaus doctor --philosophy-alignment` check catches it, and `crewhaus compile --strict` (FR-002) fails the build at compile time on any I/O-capable tool left non-external (both share one `auditToolScopes` implementation). The audit keys on `ioCapability` **or** an outward name, so a custom socket-opening tool that declares `ioCapability` is flagged even under a novel name; `--strict` additionally refuses any `mcp__*`/outward-named sink it cannot resolve to a `scope:"external"` tool offline. `buildTool` also infers `"external"` for the definitionally-outward built-in names (`Fetch`/`WebFetch`/`WebSearch`/`SendMessage`/`EvmSendTransaction`/`ImageGenerate`/`mcp__*`), but an explicit annotation on your tool is still required and still wins. The only residual a static check cannot reach is a tool that declares neither `ioCapability` nor an outward name — so declare one.
3. **A destructive tool that goes to a place the model chose sets `requireJustification: true`.** "A place the model chose" is `scope: "external"` plus a `url` or `recipient` operative argument, other than a `url` declared as its own `service` (`hasModelChosenDestination` in [packages/tool-catalog](packages/tool-catalog)): the tool sends, posts or writes where the model pointed it — `HttpRequest`, `EmailSend`, `ChatPost`, the issue and pull-request writers, `DownloadFile`, `SendMessage`, `EvmSendTransaction`. Other tools may opt in when their effect deserves an intent check (fleet mutations, secret rotation). A destructive tool that acts only inside the workspace (`Write`, `RemovePath`, `Bash`) is not required to: the permission gate already asks, and without an LLM judge a justification fails closed in production. Two companion rules for the other flags: a tool that spawns a program the workspace supplies (a project's linter, a binary in `node_modules/.bin`) is never `readOnly`, because plan mode runs read-only tools without asking; and a tool that is neither read-only nor destructive runs in auto mode without asking, so it must be one you would let run unasked. [apps/cli/src/flag-rules.test.ts](apps/cli/src/flag-rules.test.ts) holds all three over every builtin and lists the tools each one lets through, so a new tool on the permissive side is a written-down decision. The builtin table's `justify` column mirrors the flag, and `apps/cli/src/tool-registry.test.ts` holds the two together, so a bundle README reports the gate the tool really has.
4. **Authentication ≠ classification.** mTLS, JWT, and signed cookies verify *who* sent something; they say nothing about *what* the content contains. Classify after authenticating.
5. **The content-hash cache must not be bypassed for performance**; if you find yourself reaching past the classifier, you've made a security regression, not an optimization.
6. **`tool-task` keeps `classifyOutput: false`** because the sub-agent's return is already classified at the spawner boundary. Don't add a second pass at the tool layer — double-classification produces double warnings and burns the cache.
7. **Severity defaults**: malicious → replace with redaction notice; suspicious → keep + log + emit `permission_decision` trace event. Override only via explicit `opts.severity` for the source side, `opts.override` for the sink side.
8. **A tool that writes says where, so the runtime-state floor reads it right.** Mark an operative path field the tool only reads from `reads: true` (or `readsWhen: <field>`), as `CopyPath`'s `source` and `ArchiveExtract`'s `archive` are — otherwise a copy or an archive of `.crewhaus` is refused as a write into it. A tool that writes beneath a directory it names checks its targets with `@crewhaus/tool-safety/fs` (`protectedRootsOf` for the bridge's roots, then `protectedRootHolding` / `protectedRootsBeneath`, refusing with `protectedWriteRefusal`) before it writes, in every permission mode.

## Cross-cutting expectations

- **TypeScript + Bun** is the primary runtime. Python interop is reserved for slots where the ecosystem genuinely outclasses TS (today: nothing — the Claude-backed `MutationProvider` superseded the originally-deferred DSPy bridge).
- **No new package without a module brief** in [module-briefs](https://github.com/crewhaus/docs/tree/main/module-briefs). Briefs document responsibilities, depended-on / unblocks, and the catalog layer. The 0.6.0 model-plan train's packages — `packages/model-plan` (brief 307), `packages/model-service` (308) and `packages/tool-consult` (309) — are documented by briefs landing in crewhaus/docs as the release's companions (plan §12). `packages/qr-code` (brief 313), the dependency-free QR encoder behind `crewhaus hangar --lan`, follows the same rule. The 0.8.0 provability release's packages — `packages/claim-ledger` (brief 314), `packages/evaluation-service` (315), `packages/provability` (316), `packages/proof-checker` (317), `packages/tool-proof` (318), `packages/sandbox-image-z3` (319), `packages/sandbox-image-lean4` (320) and `packages/grader-provability` (321) — are documented by briefs landing in crewhaus/docs as the release's companions ([design §13](design/0.8.0-provability-release.md)).
- **A feature that is off until a spec turns it on leaves every other spec as it was.** A new block lowers spread-return-`{}`, so a spec without it compiles to the same bytes, and a test says so. A change the feature makes to every harness anyway is a deliberate default-on change, listed in the CHANGELOG with the changes that affect a harness without the block (0.8.0's "Changes that can affect a harness without `provability:`"); [scripts/default-on-changes.test.ts](scripts/default-on-changes.test.ts) finds each such change in the code and fails until that list names it, and a new kind of default-on change adds a check there and a bullet in the list.
- **Every package owns its tests**, as `*.test.ts` files beside the code in `src/`. Aim for `bun test` to stay ≥ the current pre-PR count.
- **`bun run tsc -b` and `biome check` clean** before every PR. The `.github/workflows/ci.yml` job (typecheck → test → lint) has to be green; the cross-repo `example-corpus` compile matrix now lives in [crewhaus/demos](https://github.com/crewhaus/demos).
- **Run `crewhaus doctor --philosophy-alignment`** before sending a PR that touches the IR, the eval stack, the provability gate, or any boundary site. It audits the three pillars against the current tree and exits 1 on drift.

The blocks lower to `IrEvaluation` / `IrProvability` and collapse to one `wireEvaluation` call; runtime-core receives the gates as closures (`RunEvaluation`, `RunProvability`) and never imports evaluation-service. The research shape gates its rendered report rather than a turn, through report-writer's `writeProvableReport`, which calls the same `verifyDocument`. The 0.8.0 design's rule ([design/0.8.0-provability-release.md](design/0.8.0-provability-release.md) §4.4): every new in-loop gate lands in `evaluation-service`, never in an emitter's codegen — the way routing lands in `model-service` and memory in `memory-service`. Three more rules keep the gate a check, not an opinion:
  - **claim-ledger is the one owner of the citation grammar and the claim heuristics** — sentence splitting, claim extraction, content tokens and coverage, the evidence-reference grammar, number normalization, the text fold. tool-verify, grader-continuity, grader-12-metric-rubric, report-writer and provability import it; a checker that needs one of these imports it and never keeps a copy, because two copies drift and then one tool checks a claim the other never saw. `doctor --philosophy-alignment` fails on a second definition of the citation-marker regex.
  - **`@crewhaus/provability`, `@crewhaus/claim-ledger` and `@crewhaus/proof-checker` make no model call.** The one model-backed step, the opt-in paraphrase waiver judge, is a callback evaluation-service builds and injects; `doctor --philosophy-alignment` fails if provability imports a model adapter. A sandbox checker (`smt`, `lean4`) refuses on its own without a container sandbox, so `ProofCheck` stays usable with the built-in checker everywhere; its image is built and pushed by the release's `sandbox-images` job, not by the target-shape `docker` job.
  - **Evidence is read from the run's record, never from a tool's say-so.** A builtin grounds a claim in the page or file it names only when it is a reader in provability's `READERS` table (`src/evidence.ts`: `WebFetch`, `Fetch` on GET or HEAD, `Read`), and `Retrieve`'s hits and an MCP tool's address field are the other ways in (a field the tool's declared schema lists, or, where no schema is known, the one address an input names when it carries nothing else a call could have been pointed at); every other builtin's `url` or `path` names what it acted on and grounds nothing. A new reader joins that table, and a new writing tool names its target and content fields the way the existing writers do (`TARGET_FIELDS`, `CONTENT_FIELDS` there), so the self-written mark sees what it wrote.
